# План разработки «Пульс проектов»

Этот план написан простым языком. Сначала — вся картина продукта, затем — подробный порядок создания MVP-пилота на одном проекте.

## Куда идём: продукт целиком

### 1. Сбор обратной связи

Сотрудник с телефона или компьютера видит проекты, по которым ему нужно отчитаться, и может:

- написать одну проблему или идею в одной карточке;
- отметить «проблем не заметил»;
- написать добровольно по другому проекту;
- выбрать анонимную или публичную отправку;
- приложить фото или файл;
- увидеть, что форма принята.

Обязательная сдача начинается при стадии CRM «Подготовить проект к закрытию» или по кнопке руководителя. На неё даётся 2 календарных дня. Пока все обязательные сотрудники не сдали форму, проект не переходит дальше; ручной контроль перехода остаётся у пользователя в Bitrix24.

### 2. Разбор ОКК

ОКК получает удобное рабочее место на компьютере:

- видит все карточки, фильтрует и сортирует их;
- объединяет одинаковые сообщения;
- назначает окончательного ответственного;
- фиксирует причины, решение и итог разбора;
- создаёт связанную задачу в Bitrix24;
- хранит историю изменений.

Предполагаемого ответственного до разбора видят только ОКК и администратор. После разбора сотрудникам виден только окончательно назначенный ответственный.

### 3. Задачи по итогам разбора

Приложение не заменяет задачи Bitrix24. Оно создаёт задачу по итогам разбора и показывает:

- к каким проблемам и проекту задача относится;
- кто отвечает за выполнение;
- срок задачи;
- текущий статус выполнения.

### 4. Понятная аналитика

Сотрудники и руководство видят живые графики без общего рейтинга «лучший/худший»:

- по компании — сколько форм сдано, какие есть проблемы и идеи, какие задачи поставлены;
- по проекту — кто сдал форму, какие записи появились, что решено;
- по сотруднику — публично сообщённые им проблемы, окончательно назначенные ему проблемы, календарные дни с последней подтверждённой проблемой, предложенные и реализованные инициативы.

Из любого графика можно открыть карточку, из которой получилась цифра.

### 5. Администрирование

Администратор имеет функции всех ролей и может:

- управлять ролями и правилами обязательной сдачи;
- видеть автора анонимного сообщения;
- отменять окончательное назначение ответственности;
- настраивать справочники, проекты и связь с Bitrix24.

### 6. Улучшения после MVP

После успешного пилота добавляем по очереди:

- напоминания о несданных формах и автоматическое закрытие задачи о сдаче формы;
- сохранение черновика на телефоне и продолжение заполнения при плохом интернете;
- подсказки ОКК о похожих карточках без автоматического объединения;
- шаблоны контрольных точек для разных типов проектов;
- шаблон акта разбора;
- подробную ленту изменений: кто, что и почему поменял;
- email-дайджесты для руководителей;
- отчёты о повторяющихся причинах и реализованных инициативах;
- выгрузки в XLSX, CSV и API для других программ;
- новые интеграции, когда появится конкретная польза от них.

## MVP-пилот: подробный порядок работ

### Шаг 1. Подготовить основу

1. Создать отдельную тестовую версию приложения и отдельную рабочую версию.
2. Разместить приложение на сервере в собственном наборе Docker-контейнеров, не смешивая его с другими приложениями.
3. Подключить локальное приложение к облачному Bitrix24.
4. Настроить вход сотрудника через Bitrix24 и четыре роли: сотрудник, руководитель, ОКК, администратор.
5. Проверить, что анонимный автор виден только администратору.

**Готово, когда:** можно безопасно открыть пустое приложение из Bitrix24 и войти под разными ролями.

### Шаг 2. Подтянуть один проект и участников

1. Выбрать один реальный или тестовый CRM-проект для пилота.
2. Подтянуть название проекта и список сотрудников из Bitrix24.
3. Отметить, кто обязан сдать форму, а кто может написать добровольно.
4. Настроить два запуска обязательной формы: стадия «Подготовить проект к закрытию» и кнопка руководителя.
5. Запустить отсчёт 2 календарных дней и пометку «просрочено».
6. Показать, кто не сдал форму и у кого просрочка; ручной «стоп-кран» перехода проекта дальше остаётся у пользователя в Bitrix24 через его контрольную задачу.

**Готово, когда:** по одному проекту у каждого человека виден понятный список того, что ему нужно сдать.

### Шаг 3. Сделать форму сотрудника

1. Создать мобильную форму с крупными кнопками и русским текстом.
2. Добавить выбор: проблема была или проблем не заметил.
3. Сделать правило «одна проблема или идея — одна карточка».
4. Добавить тип: ошибка, нарушение процесса, идея или инцидент.
5. Добавить описание, предложение решения, анонимность и фото/файлы.
6. Показать в форме понятную фразу: предполагаемый ответственный — внутреннее поле, указанному человеку оно не показывается до разбора.
7. Сжать большие фото перед хранением.

**Готово, когда:** сотрудник может с телефона сдать форму и сразу увидеть подтверждение.

### Шаг 4. Сделать рабочее место ОКК

1. Показать список всех карточек по проекту.
2. Добавить поиск и фильтры: период, проект, подразделение, сотрудник, тип, статус, анонимная/публичная запись, задача, просрочка, «ждёт разбора».
3. Сделать карточку разбора: комментарии, окончательное назначение, причины, решение и связь с другими карточками.
4. Добавить ручное объединение одинаковых сообщений и возможность администратору отменить ошибочное объединение.
5. Добавить массовые действия: поменять статус, тип, проект или предполагаемого ответственного у нескольких карточек.
6. Сделать понятные статусы: «Новая», «Ждёт разбора», «На разборе», «Задачи поставлены», «Закрыта».

**Готово, когда:** ОКК может провести разбор одного проекта без таблиц и ручного сведения сообщений.

### Шаг 5. Связать итог разбора с Bitrix24

1. В карточке разбора сделать кнопку «Создать задачу в Bitrix24».
2. Перед созданием дать ОКК проверить текст, ответственного, срок и наблюдателей.
3. Передать задачу в Bitrix24 и сохранить ссылку обратно в карточку.
4. Показывать в приложении статус этой задачи.

**Готово, когда:** руководитель открывает карточку проблемы и понимает, какая задача была поставлена и как она выполняется.

### Шаг 6. Сделать первые дашборды

1. Сделать три страницы: компания, проект и сотрудник.
2. Добавить понятные цифры и графики без перегрузки.
3. Сделать переход из каждого графика к исходным карточкам.
4. Добавить светлую и тёмную темы.
5. Сделать PDF-выгрузку только для администратора.

**Готово, когда:** на телефоне и компьютере видно, что происходит с проектом, без обращения к отдельным таблицам.

### Шаг 7. Показать все будущие разделы

1. В интерфейсе оставить вкладки будущих функций.
2. На каждой такой вкладке показать плашку «Будет в следующем релизе».
3. Коротко объяснить, что появится на вкладке, и показать примерный вид.

**Готово, когда:** пользователь видит всю будущую картину продукта, но не путает готовые функции с планами.

### Шаг 8. Провести пилот и решить, что улучшать

1. Сначала заполнить чистый тестовый лист и проверить все сценарии.
2. Очистить тестовые данные.
3. Провести один настоящий проект через приложение.
4. Собрать замечания сотрудников, руководителей и ОКК.
5. Исправить неудобные места до общего запуска.
6. Проверить, что данные можно восстановить из резервной копии и что администратор получает технические письма.

**Готово, когда:** один проект прошёл от сдачи форм до разбора, задач Bitrix24 и итоговых графиков без обходных таблиц.

## Что пока не делаем

- не строим отдельную систему срочных инцидентов: для неё уже есть действующий порядок вне приложения;
- не вводим рейтинг сотрудников;
- не добавляем распознавание текста на фото и PDF;
- не переносим старую историю данных;
- не запускаем сложные подсказки, автоматические решения и дополнительные выгрузки до результатов пилота.
