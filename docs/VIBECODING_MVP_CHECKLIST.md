# Чек-лист вайбкодинга MVP

Это рабочий маршрут для создания первого MVP вместе с Codex. Идти строго по порядку: после каждого пункта открыть приложение, проверить результат и только потом переходить дальше.

## Сколько займёт

Ориентир — **8–12 рабочих дней активной работы** с Codex. Это не означает 8–12 календарных дней: доступ к Bitrix24, серверу и ваши проверки могут растянуть срок. Первую живую версию формы можно увидеть примерно через **3–4 рабочих дня**.

## Как пользоваться

1. Открыть один пункт.
2. Скопировать его промпт в Codex.
3. Дождаться результата, открыть приложение и проверить список «Готово, когда».
4. Если что-то не нравится — написать, что именно изменить, не переходя к следующему пункту.
5. После проверки написать: «Пункт N принят, переходим к N+1».

## 0. Подготовить доступы и место работы

**Что делаем:** создаём отдельную папку проекта, подключаем GitHub, готовим тестовый домен/сервер и позже выдаём доступ к Bitrix24.

**Промпт для Codex:**

> Проверь репозиторий app-feedback-collection. Подготовь локальное окружение для разработки MVP «Пульс проектов»: отдельную тестовую настройку и рабочую настройку, без запуска на моём сервере. Не добавляй секреты в Git. Сначала покажи, какие данные и доступы мне нужно выдать для Bitrix24 и сервера.

**Готово, когда:** есть понятный список доступов, а проект можно запустить на вашем компьютере.

## 1. Собрать пустой каркас приложения

**Что делаем:** создаём приложение с входом, меню, светлой/тёмной темой и двумя версиями экрана: телефон и компьютер.

**Промпт для Codex:**

> Создай первый каркас MVP «Пульс проектов». Нужны: русское меню, светлая и тёмная темы, мобильный вид для сотрудников и широкий вид для ОКК. Сделай разделы: «Главная», «Мои формы», «Проекты», «Разборы», «Аналитика», «Настройки». Не делай рабочую логику будущих разделов: покажи в них красивую плашку «Будет в следующем релизе» с коротким описанием. После работы запусти проверку и покажи, как открыть приложение.

**Готово, когда:** приложение открывается, меню переключается, тема меняется, а на телефоне всё помещается без мелких кнопок.

## 2. Сделать роли и безопасную видимость

**Что делаем:** добавляем сотрудника, руководителя, ОКК и администратора. Администратор умеет всё, анонимного автора видит только он.

**Промпт для Codex:**

> Добавь в MVP четыре роли: сотрудник, руководитель, ОКК, администратор. Администратор имеет функции всех ролей и один видит автора анонимной записи. Предполагаемый ответственный виден только ОКК и администратору. Сотрудник видит только окончательное назначение после разбора. Добавь тестовые учётные записи для проверки каждой роли и не используй настоящие данные Bitrix24.

**Готово, когда:** вход под разными ролями показывает разные возможности, а данные анонимного автора не появляются у сотрудника и руководителя.

## 3. Подключить проекты и обязательные формы

**Что делаем:** сначала на тестовых данных, затем через Bitrix24 получаем проект и его участников. Показываем, кому нужно сдать форму.

**Промпт для Codex:**

> Сделай раздел «Мои формы». На тестовых данных покажи список проектов, по которым сотрудник обязан сдать форму. Добавь два способа запуска: стадия «Подготовить проект к закрытию» и кнопка руководителя. После запуска даётся 2 календарных дня, потом появляется пометка «Просрочено». Приложение не меняет стадию проекта само: оно только показывает несдавших, потому что ручной контроль перехода остаётся в Bitrix24 у владельца процесса.

**Готово, когда:** на экране сотрудника видно, какую форму и до какой даты нужно сдать.

## 4. Сделать форму обратной связи

**Что делаем:** сотрудник создаёт отдельную карточку проблемы или идеи либо отмечает «проблем не заметил».

**Промпт для Codex:**

> Сделай мобильную форму обратной связи для MVP. Поля: проект, «проблемы были / проблем не заметил», тип записи (ошибка, нарушение процесса, идея, инцидент), заголовок, описание, предложение решения, фото или файл, анонимно/публично. Одна карточка — одна проблема или идея. Добавь внутреннее поле «предполагаемый ответственный» для ОКК/администратора и понятное пояснение, что указанному человеку оно не показывается до разбора. Добавь понятное подтверждение после отправки.

**Готово, когда:** форму удобно заполнить одной рукой на телефоне, а отправленная карточка появляется в «Мои формы».

## 5. Сделать список и карточку разбора ОКК

**Что делаем:** ОКК видит все сообщения проекта, читает, сортирует и разбирает их.

**Промпт для Codex:**

> Сделай рабочее место ОКК для MVP на компьютере. Нужны список карточек и страница одной карточки. Добавь фильтры: период, проект, подразделение, сотрудник, тип, статус, анонимная/публичная запись, есть ли задача, просрочена ли задача, «ждёт разбора». В карточке добавь комментарии, окончательного ответственного, причину, решение, связь с задачей и историю изменений. Статусы: «Новая», «Ждёт разбора», «На разборе», «Задачи поставлены», «Закрыта».

**Готово, когда:** ОКК может без таблиц найти нужную проблему и оформить результат разбора.

## 6. Добавить одинаковые сообщения и массовые действия

**Что делаем:** ОКК вручную объединяет дубли; администратор может отменить ошибочное объединение.

**Промпт для Codex:**

> Добавь ручную работу с дублями. ОКК может выбрать главную карточку и присоединить к ней похожую карточку. Администратор может отменить это действие. Добавь массовое изменение статуса, типа, проекта и предполагаемого ответственного для выбранных карточек. Все изменения записывай в историю карточки: кто и когда что сделал.

**Готово, когда:** две одинаковые записи можно объединить, а ошибочное объединение можно отменить без потери текста.

## 7. Создать задачу в Bitrix24 по итогу разбора

**Что делаем:** ОКК создаёт настоящую задачу Bitrix24 из карточки разбора.

**Промпт для Codex:**

> Подключи создание задачи Bitrix24 из карточки разбора. Перед созданием покажи форму проверки: название задачи, текст, ответственный, наблюдатели, срок. После создания сохрани ссылку на задачу в карточке и показывай её статус. Если Bitrix24 временно недоступен, не теряй данные и покажи понятную ошибку; не создавай дубли задач при повторном нажатии.

**Готово, когда:** из карточки можно открыть созданную задачу Bitrix24 и понять, почему она поставлена.

## 8. Сделать первые графики

**Что делаем:** добавляем три простых дашборда: компания, проект, сотрудник.

**Промпт для Codex:**

> Сделай первые дашборды MVP с понятными интерактивными графиками, без рейтинга сотрудников. Нужны страницы «Компания», «Проект», «Сотрудник». Покажи сдачу форм, количество проблем и идей, статусы разборов и задач. У сотрудника покажи публично сообщённые им проблемы, окончательно назначенные ему проблемы, календарные дни с последней подтверждённой проблемой, предложенные и реализованные инициативы. Из цифры или графика должен быть переход к исходным карточкам.

**Готово, когда:** цифру на графике можно проверить, открыв соответствующие карточки.

## 9. Добавить PDF и будущие вкладки

**Что делаем:** администратор скачивает короткий отчёт; пользователь видит будущую картину продукта.

**Промпт для Codex:**

> Добавь PDF-выгрузку только для администратора: выбранный проект, период, основные цифры, список связанных задач и ссылочные номера карточек. Дополни будущие вкладки плашкой «Будет в следующем релизе», описанием пользы и примерным видом: напоминания, шаблоны актов, журнал изменений, расширенные отчёты, выгрузки XLSX/CSV/API, новые интеграции.

**Готово, когда:** администратор может получить понятный PDF, а сотрудник не видит кнопку выгрузки.

## 10. Проверить на тестовом проекте

**Что делаем:** проходим весь путь от формы до задачи и графика на чистых тестовых данных.

**Промпт для Codex:**

> Проведи полный тест MVP «Пульс проектов» на чистых тестовых данных. Проверь четыре роли, анонимность, две формы сотрудника, ручной запуск обязательной формы, 2-дневную просрочку, разбор ОКК, дубль, создание задачи Bitrix24, графики, PDF и телефонный экран. Составь короткий список найденных проблем по важности и исправь только критичные после моего подтверждения.

**Готово, когда:** один тестовый проект проходит весь путь без таблиц и ручного переноса информации.

## 11. Провести один живой пилот

**Что делаем:** очищаем тестовые данные и запускаем MVP на одном настоящем проекте.

**Промпт для Codex:**

> Подготовь MVP «Пульс проектов» к пилоту на одном проекте. Не меняй данные без моего подтверждения. Проверь резервную копию, доступы ролей, письмо администратору при технической проблеме и короткую инструкцию для сотрудников. Составь список действий для старта пилота и для его завершения.

**Готово, когда:** один настоящий проект завершён с формами, разбором, задачами и итоговым графиком.

## Когда переходить к следующим релизам

Переходим только после того, как пилот показал, что сотрудники действительно сдают формы, ОКК не возвращается к таблицам, а поставленные задачи можно связать с причинами. Тогда первым следующим релизом берём напоминания, черновики на телефоне и шаблоны актов разбора.
